# Roadmap

Build in small, verifiable phases. Early milestones are internal slices, not reduced release scope. The [user specification](user-specification.md) is the first-release acceptance baseline.

| Phase | Work | Exit check |
| --- | --- | --- |
| 1. Prove the offline path | Take one short Markdown source and one Clinical Decision through a minimal versioned XML schema, inference, and a shared React and TypeScript UI using HeroUI. Use the six-week follow-up example as the fixture. | The generated `index.html` opens from disk with networking disabled, and HeroUI controls are styled and interactive. Synthetic cases cover applies, does not apply, and unknown; the applicable case shows a 1% Do-Not-Consider Score, not a clinical probability. |
| 2. Verify multi-decision builds | Add separate coverage and test reports, explicit partial-build labeling, and non-destructive rebuilds. Route large builds by topic or scenario before asking for relevant Case Inputs. Show the next step, why it appeared, a short citation, and relevant missing inputs. | A mixed fixture separates verified guidance from Unresolved Decisions, flags verification failures by decision, and preserves the previous build on rerun. Cases distinguish unknown from no and apply numeric thresholds in the relevant units. |
| 3. Add offline case exploration | Add a tornado chart for the selected option in each modeled decision and a What-If Sandbox with side-by-side guidance and scores and a reset to the original inputs. Keep model assumptions fixed in both features. | Offline tests confirm that bars vary one input at a time, cover all valid categories or use defined numeric ranges and thresholds, and show tested values and units. Inapplicable states name the source condition and are not scored. When comparisons are not meaningful, the app explains why and keeps the sandbox available. Multi-input sandbox edits and reset leave the original case unchanged. |
| 4. Scale Markdown discovery | Map long sources, persist resumable section progress, extract exact decision-relevant passages, reconcile overlaps and exceptions, and make a second coverage pass. | An interrupted multi-section build resumes and accounts for decisions in prose, tables, figures, and footnotes. Equivalent decisions merge without collapsing distinctions that change guidance. |
| 5. Expand document intake | Normalize DOCX, PDF, and common images to Markdown, including OCR for scanned pages. Preserve originals and check decision-changing conversion damage against them. | Fixtures cover each supported input type and show that unsupported or unreadable sections are reported without silently dropping them. |
| 6. Fill evidence gaps | Add bounded external evidence review and conflict resolution. Label Proxy Estimates and check whether varying a proxy changes guidance during the build, separately from the app’s Case Input exploration. | Fixtures show a justified conflict resolution, an unresolved conflict, a labeled proxy with its effect on guidance, and an unresolved numeric output that does not suppress directly supported guidance. |
| 7. Package and verify the first release | Ship the shared workflow for Codex, Claude, and OpenCode through both installation paths. Run the full specification checks on representative builds. | Both paths install the same release, each host can build a CDSS, and the generated folder contains `index.html`, XML networks, and separate coverage and test reports. The research-only app works offline directly from disk without the host. |
